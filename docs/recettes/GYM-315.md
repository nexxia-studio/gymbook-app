# Recette — GYM-315 · rejeu d'un webhook Mollie par le cockpit

> Un lot, un fichier. Voir `docs/recettes/README.md`.

Fonction : `admin-replay-mollie-webhook` (`verify_jwt = true`, **`super_admin` uniquement**).
Outil d'exploitation **éditeur** : il n'y a pas d'écran gérant, et il ne doit pas y en avoir.

⚠️ Aucune migration. `audit_logs` existe déjà (baseline) et n'est pas modifiée.

## Appel

```bash
curl -X POST "$SUPABASE_URL/functions/v1/admin-replay-mollie-webhook" \
  -H "Authorization: Bearer <JWT_SUPER_ADMIN>" \
  -H "Content-Type: application/json" \
  -d '{"mollie_payment_id":"tr_xxx"}'          # + "target" si la déduction est à forcer
```

## Autorisation

| # | geste | attendu |
|---|---|---|
| A1 | 🔴 Appeler avec un JWT **`gym_admin`** | **403 `FORBIDDEN`**. C'est LE point du lot : toutes les autres `admin-*` acceptent `gym_admin`, celle-ci le refuse |
| A2 | Appeler avec un JWT **membre** | 403 `FORBIDDEN` |
| A3 | Appeler **sans** en-tête `Authorization` | 401 `UNAUTHORIZED` |
| A4 | Appeler avec la **clé anon** (publique) | 401/403 — jamais 200. `verify_jwt` seul n'autorise rien |
| A5 | 🔴 JWT `super_admin` dont le profil a `deleted_at` renseigné | **403**. Même définition que `public.is_super_admin()` en base |
| A6 | Le message de refus | ne dit **ni** le rôle constaté, **ni** « vous êtes gym_admin » |

## Entrée et rejeu à l'aveugle

| # | geste | attendu |
|---|---|---|
| B1 | 🔴 `mollie_payment_id` **inconnu en base** (`tr_INVENTE`) | **404 `PAYMENT_NOT_FOUND`**, aucun appel à la cible |
| B2 | `mollie_payment_id` malformé (`DROP TABLE`) | 400 `INVALID_MOLLIE_PAYMENT_ID` |
| B3 | `mollie_payment_id` absent | 400 `MISSING_MOLLIE_PAYMENT_ID` |
| B4 | 🔴 `target` hors liste fermée (ex. `delete-account`) | **400 `INVALID_TARGET`**. Le secret ne part que vers les deux webhooks Mollie |
| B5 | Id d'une **vente au comptoir** (espèces/TPE) | 404 — elles n'ont pas de `mollie_payment_id`, aucun webhook ne les concerne |
| B6 | Méthode `GET` | 405 |

## Rejeu

| # | geste | attendu |
|---|---|---|
| C1 | 🔴 Paiement d'abonnement **déjà `paid`** | 200, `changed: false`, `status_before` = `status_after` = `paid`. **No-op** : les gardes de la cible sortent proprement, aucune écriture métier, aucun double abonnement |
| C2 | 🔴 Paiement figé en `pending` (le cas GYM-314, après déploiement du correctif) | 200, `changed: true`, `pending → paid`. Le membre peut réserver, **sans aucun geste en base** |
| C3 | Paiement à `credits_granted = 0` | `target: "mollie-subscription-webhook"`, `target_source: "deduced"` |
| C4 | Paiement à `credits_granted > 0` | `target: "mollie-webhook"`, `target_source: "deduced"` |
| C5 | `target` passé explicitement | `target_source: "explicit"`, la déduction est ignorée |
| C6 | Rejouer **11 fois en 60 s** le même id | la cible applique son propre rate limit (10/60 s) et rend 200 « OK » sans traiter. Rien à corriger ici — c'est sa garde, on ne la contourne pas |

## Secret et trace

| # | geste | attendu |
|---|---|---|
| D1 | 🔴 Lire les logs de la fonction après un rejeu | **aucune occurrence** de `MOLLIE_WEBHOOK_SECRET`. Une seule ligne : `replay by <uuid> → <cible> for <id>` — le **nom** de la cible, jamais l'URL |
| D2 | 🔴 Lire la réponse JSON | aucun secret, aucune URL construite |
| D3 | 🔴 Provoquer une panne réseau vers la cible | `transport_error` est **caviardé** (`secret=[redacted]`). En Deno le message de `fetch` porte l'URL appelée — c'est le chemin de fuite le plus facile à manquer |
| D4 | 🔴 Retirer `MOLLIE_WEBHOOK_SECRET` de l'environnement, rejouer | **500 `CONFIG_ERROR`**, aucun appel. ⚠️ Sans cette garde le rejeu rendrait **200 « OK »** : les cibles répondent 200 sur secret refusé comme sur succès — un faux succès sur de l'argent |
| D5 | 🔴 Après chaque rejeu : `select * from audit_logs where action = 'mollie_webhook_replay'` | une ligne : `actor_id` (qui), `created_at` (quand), `resource_id` + `new_data.mollie_payment_id` (quel paiement), `new_data.http_status` / `status_before` / `status_after` / `ok` (quel résultat) |
| D6 | Vérifier `new_data` | contient le **nom** de la cible, jamais l'URL |
| D7 | Cas refusé (A1, B1) | **aucune** ligne `audit_logs` — on ne trace que les rejeux réellement partis |
| D8 | Se connecter en `gym_admin` de la salle concernée | il **voit** la ligne (RLS « Gym admins voient les logs de leur gym »). Assumé : une intervention de l'éditeur sur les paiements d'une salle doit être visible par cette salle |

## Checklist de déploiement

**Aucune dépendance d'ordre** — la fonction est nouvelle, personne ne l'appelle, et elle ne
modifie aucune fonction existante. Elle peut être déployée seule, à tout moment.

⚠️ **Prérequis** : le correctif GYM-314 doit être en prod **avant** de rejouer les deux
paiements bloqués. Rejouer sans lui reproduirait le 422 — le rejeu échouerait proprement
(dead-letter + 503), mais ne réparerait rien.

### Staging

1. `supabase functions deploy admin-replay-mollie-webhook --project-ref <STAGING>`
2. Vérifier que `MOLLIE_WEBHOOK_SECRET` est bien présent sur le projet (`supabase secrets list`) — **la valeur ne s'affiche pas et n'a pas à l'être**.
3. Passer **A1 → A6** (autorisation) et **B1 → B6** (entrée). Aucun de ces cas ne doit produire d'appel à une cible.
4. Passer **C1** sur un paiement de test déjà `paid` → `changed: false`.
5. Passer **D1, D2, D5** : logs propres, réponse propre, une ligne d'audit.
6. Passer **D4** : retirer temporairement le secret, vérifier le 500, **le remettre**.

### Production

7. `supabase functions deploy admin-replay-mollie-webhook --project-ref <PROD>`
8. **`supabase secrets list`** — confirmer `MOLLIE_WEBHOOK_SECRET`. Un secret absent en prod rendrait 500 (D4), pas un faux succès : c'est le comportement voulu, mais autant le savoir avant.
9. Re-passer **A1** et **B1** en prod (les deux refus), sur un id inventé. Sans effet, et ils confirment que la garde est bien active.
10. 🔴 **Réparer les deux membres de l'inauguration** — un rejeu chacun, en notant les `mollie_payment_id` :
    - attendu : `changed: true`, `status_before: "pending"`, `status_after: "paid"` ;
    - si `changed: false` avec `status_after: "pending"`, **s'arrêter** et lire `response_body` — le correctif GYM-314 n'est pas actif, ou un autre défaut suit.
11. Vérifier pour chacun : une ligne `member_subscriptions` existe, et le membre peut réserver depuis l'app.
12. Vérifier les deux lignes `audit_logs` (D5) — c'est la trace de l'intervention sur de l'argent réel.

### Retour arrière

Supprimer la fonction (`supabase functions delete admin-replay-mollie-webhook`). Aucun état
à défaire : elle n'écrit que dans `audit_logs`, et n'a modifié aucune fonction existante.
