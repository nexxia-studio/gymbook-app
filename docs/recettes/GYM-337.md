## 1. `googleServicesFile` — une fois, dans le bloc commun

Le cockpit a enregistré les **trois** applications dans **un seul** projet Firebase (`viniz-54637`). Le fichier porte donc les trois clients, et c'est le plugin Gradle de Google qui choisit celui dont le `package_name` correspond à l'`applicationId` de la build.

Le chemin ne **diffère pas** d'une variante à l'autre : il n'a rien à faire dans un bloc de variante. C'est aussi la règle posée par GYM-258 — la configuration Dopamine s'écrit d'un seul tenant, les variantes n'**altèrent** que ce qui change. Trois copies seraient trois endroits où l'oublier, et ce fichier sait déjà ce que ça coûte : le bloc `isViniz` porte en toutes lettres une icône « pas posée ici — manque connu ».

**`.gitignore` vérifié** : `git check-ignore` ne matche pas le fichier. Il n'était simplement jamais passé par `git add`. Il ne contient que des identifiants publics, embarqués en clair dans chaque APK — il doit être versionné.

**Rien côté iOS**, et c'est normal : les notifications y passent par APNs via Expo, sans Firebase.

## 2. Le canal Android — ce qu'il corrige n'est pas ce qu'on croit

> ⚠️ **Correction d'une prémisse du cadrage.** « Sur Android 8+ un canal est obligatoire : même avec un jeton valide, rien ne s'afficherait. » Android exige bien un canal — mais **expo-notifications en crée un tout seul**. Vérifié dans le code natif de la version installée (0.32.17, `BaseNotificationBuilder.kt:101-137`) : un message sans `channelId` part dans `expo_notifications_fallback_notification_channel`, créé à la volée en `IMPORTANCE_HIGH`, badge et vibration actifs.
>
> Les notifications **se seraient donc affichées** une fois FCM configuré. Le défaut est réel mais de nature différente : elles arrivent dans un canal générique, nommé par une ressource Android (« Miscellaneous » / « Divers »), que le membre ne peut ni identifier ni régler, et dont l'app ne choisit ni le nom ni l'importance. Les deux correctifs restent nécessaires — mais c'est le point 1, seul, qui débloque la réception.

**Le canal côté app était nécessaire mais pas suffisant.** `send-notification` n'envoyait aucun `channelId` : le canal déclaré n'aurait jamais été utilisé. Le lot ajoute donc `channelId: 'default'` au message Expo, à tenir égal à `ANDROID_CHANNEL_ID` côté app.

**Rétrocompatible, vérifié sur le même fichier** (`l. 64-75`) : si le canal demandé n'existe pas — tout binaire antérieur à ce lot — expo-notifications journalise et retombe sur son canal de repli. Rien n'est perdu pendant que le parc se met à jour.

### La couleur : ni celle du plugin, ni une autre — aucune

**Réponse à la question posée : le canal ne doit porter AUCUNE couleur.**

`importance` et les lumières d'un canal sont **immuables après création** — Android laisse le contrôle de ces comportements au membre. Reprendre le `#C8F000` des `plugins[]` (le lime Dopamine, faux pour Viniz — c'est GYM-324, hors lot) le **graverait dans chaque installation** : GYM-324 aurait alors deux endroits à corriger, dont un que le correctif ne pourrait **pas** atteindre sans changer l'identifiant du canal.

La teinte de l'icône reste où elle est, dans le plugin : une seule source, corrigible en une fois.

**Importance `MAX`** (heads-up), et c'est le même choix que le canal de repli d'Expo — donc aucune régression de comportement. Justification : une place de liste d'attente se confirme en 30 minutes ; une notification qui n'apparaît pas à l'écran fait perdre la place.

**Nom et description traduits** : ce sont les deux seuls champs qu'Android laisse modifiables après création, donc un changement de langue les met à jour au redémarrage suivant.

## 3. Cesser d'avaler l'échec

```diff
-    } catch (e) {
-      console.log('[Push] Registration failed (non-blocking):', e)
-      return null
-    }
+    } catch (e) {
+      console.error('[Push] Registration failed (non-blocking):', e)
+      Sentry.captureException(e, { tags: { area: 'gym337_push_token' }, … })
+      return null
+    }
```

Plus un contrôle qui n'existait pas : `getExpoPushTokenAsync` peut rendre une valeur vide **sans lever**. Permission accordée et aucun jeton → `Sentry.captureMessage(level: 'error')`. Sans lui, ce cas se confondait avec le refus de permission.

**Un refus de permission ne remonte rien** : c'est un choix légitime du membre, et l'alerte utile se noierait dans le bruit.

> 🔴 **Un troisième silence, trouvé en chemin et corrigé.** L'écriture du jeton en base n'était pas « avalée par le catch » — elle n'était **même pas lue** : `supabase.from().update()` ne lève pas sur erreur, il rend `{ error }`. Le `try/catch` d'origine ne pouvait rien attraper et la valeur de retour était jetée. Un jeton obtenu mais jamais stocké est aussi muet qu'un jeton absent.

## Recette

Les étapes **R1 à R3 exigent une build Android sur appareil réel** — voir la réponse (c) plus bas.

| id | étape | attendu |
|---|---|---|
| **R1** | Installer une build `preview`, se connecter, accepter la permission | une ligne `push_token` non nulle sur le profil : `SELECT push_token FROM profiles WHERE id = '<uuid>'` |
| **R2** | Déclencher une notification (rejoindre une liste d'attente pleine, puis libérer une place) | la notification **s'affiche**, en heads-up |
| **R3** | Paramètres Android → Applications → *l'app* → Notifications | une catégorie **« Réservations et rappels »**, et non « Divers » / « Miscellaneous » |
| **R4** | Refuser la permission, relancer | **aucun** événement Sentry (un refus n'est pas une anomalie) |
| **R5** | Désinstaller / réinstaller, se reconnecter | `push_token` **mis à jour** avec la nouvelle valeur |

> **R3 est le contrôle qui distingue « ça marche » de « ça marche par le canal de repli ».** Sans lui, R2 réussirait aussi avec un canal générique.

## À rapporter sans coder

### (a) Le jeton est-il ré-enregistré s'il a changé ? — **oui, à chaque démarrage**

`usePushNotifications(userId)` est monté dans `app/_layout.tsx:280`, et son effet a `[userId]` en dépendance : au lancement, `userId` passe de `null` à sa valeur, l'effet rejoue, un jeton est redemandé, et **l'écriture est inconditionnelle** (aucune comparaison avec la valeur en base). Réinstallation, restauration de sauvegarde, effacement des données : le jeton neuf écrase l'ancien au premier lancement.

La boucle se referme côté serveur : `send-notification` met `push_token` à `NULL` sur `DeviceNotRegistered`, et le démarrage suivant en repose un valide.

⚠️ **Le trou qui reste** : `Notifications.addPushTokenListener` n'est utilisé **nulle part**. FCM et APNs peuvent faire tourner un jeton **en cours de session** ; il n'est alors capté qu'au redémarrage suivant, et entre les deux les push partent sur un jeton périmé — silencieusement, `DeviceNotRegistered` nettoyant sans alerter. Faible volume, réel quand même. Hors lot.

### (b) D'autres endroits où un échec de push est avalé ? — **oui, à trois niveaux**

1. **Le client** — les deux corrigés ici (jeton, écriture en base).
2. **`send-notification` lui-même est plutôt diligent** : il journalise les non-2xx, compte `sent` / `failed`, nettoie les jetons morts et retourne le tout. Mais 🔴 **`failed` n'est alerté nulle part** : aucun Sentry dans les edge functions (vérifié — zéro occurrence sous `supabase/functions/`), aucun dead-letter pour les push. **C'est ce qui a masqué GYM-337 côté serveur** : sans FCM, chaque envoi Android revenait en erreur Expo, `failed` s'incrémentait, et le compteur partait dans une réponse HTTP que personne ne lit.
3. **Les appelants, inégaux** :
   - `notify-waitlist:158` est **exemplaire** — il vérifie `sent >= 1` et journalise « push NOT delivered » sinon ;
   - `send-reminders:112` ne capte que l'erreur **réseau** (`.catch`) : un 200 avec `sent: 0, failed: 1` passe sans un mot ;
   - `admin-lift-suspension:145`, `mollie-webhook:370`, `mollie-subscription-webhook:794` : `await fetch(...)` sans lire la réponse.

**Recommandation** : porter le contrôle de `notify-waitlist` dans un helper partagé, et faire remonter `failed > 0` dans `webhook_failures` — la boîte aux lettres que le cockpit relève déjà (GYM-338). Hors lot.

### (c) La recette des lots de notification doit-elle inclure un build Android ? — **oui**

C'est la seule réponse cohérente avec ce qui vient d'arriver. **Le défaut est invisible sur iOS par construction** : iOS passe par APNs via Expo, sans Firebase. Aucun test iOS, si complet soit-il, ne pouvait le révéler — et c'est pour cela qu'il a vécu depuis le premier jour.

Deux précisions qui comptent :

- **Expo Go ne suffit pas.** Le hook sort dès `Constants.appOwnership === 'expo'` (l. 28) : en Expo Go, rien ne s'enregistre et rien n'échoue. Il faut une *development build* ou une build EAS.
- **Le canal ne se voit que sur un APK.** `googleServicesFile` n'est lu que par le plugin Gradle, pendant le build natif : aucun `expo config` ne prouve qu'il a été consommé.

**Étape à ajouter au gabarit** : « build Android (profil `preview`) installée sur un appareil réel — notification reçue **et** canal visible sous son nom lisible dans les paramètres ». Le second contrôle est celui qui distingue une vraie réussite d'un repli silencieux.
