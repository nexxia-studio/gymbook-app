## Le garde-fou : deux moitiés disjointes

Un trigger qui **créerait** l'adhésion a été écarté : il masquerait les appelants fautifs, et surtout il rendrait le prochain chemin ajouté **structurellement dépendant** de lui — plus personne n'écrirait l'insertion, et la règle cesserait d'exister dans le code pour ne survivre que dans un trigger.

Un trigger qui **refuse** a les qualités inverses : l'appelant fautif échoue bruyamment, par son nom, à la première exécution. Il rend la divergence *impossible* au lieu de la rattraper. Et ce n'est pas un trigger de plus — `trg_gym_id_immutable` existe déjà et fait déjà ce travail pour X→Y ; il lui manquait NULL→X.

Il ne peut pas couvrir `service_role` : les edge functions doivent pouvoir poser `gym_id`, et un refus en cours d'instruction les casserait toutes. Pour elles, la garde est la **veille horaire**.

**Trigger pour le client → impossible. Veille pour le serveur → visible.**

## Recette

### 1. Le trigger refuse un PATCH client NULL → X (le test qui compte)

Avec le JWT d'un membre **sans salle** :

```sql
UPDATE profiles SET gym_id = '<n''importe quelle salle>' WHERE id = auth.uid();
```

**Attendu : `42501 GYM_ID_IMMUTABLE`.** Avant ce lot, **cet UPDATE passait** — et c'est la faille : en multi, tout compte sans salle (inscription OAuth, ou signup refusé au plafond) pouvait se rattacher à la salle de son choix, sans code d'adhésion, sans plafond de plan, sans facturation.

**Non-régression** — insérer l'adhésion puis rejouer le même UPDATE : **accepté**. La bascule vers une appartenance existante n'a pas bougé.

### 2. Un test par chemin fautif

| chemin | geste | attendu |
|---|---|---|
| `create_gym_self_serve` | créer une salle en self-serve | `member_gyms` porte le **gérant** |
| `invite-team-member` | inviter un coach / gérant | adhésion + salle + rôle, sur un compte neuf |
| `healProfile` | login Apple/Google sur l'app single | adhésion + salle posées ensemble |
| `ensureProfile` (repli) | profil absent au login | profil créé **nu**, puis `claim_app_gym` |

Contrôle commun, après chaque geste :

```sql
SELECT p.id, p.gym_id, (mg.member_id IS NOT NULL) AS a_une_adhesion
  FROM profiles p
  LEFT JOIN member_gyms mg ON mg.member_id = p.id AND mg.gym_id = p.gym_id
 WHERE p.id = '<uuid>';
```

**Attendu : `a_une_adhesion = true`.**

### 3. `claim_app_gym` refuse une salle non dédiée

Avec le JWT d'un membre sans salle, viser une salle du parcours multi :

```sql
SELECT public.claim_app_gym('<salle sans dedicated_app_gym>');
```

**Attendu : `PT403 GYM_NOT_DEDICATED_APP`.** Sans ce contrôle, la RPC serait exactement la faille qu'on ferme, avec un nom plus rassurant.

### 4. La veille ouvre **une** ligne, pas vingt-quatre

Fabriquer une divergence (retirer une ligne `member_gyms` d'un profil rattaché), puis :

```sql
SELECT public.member_gyms_drift();  -- ×3
SELECT count(*) FROM webhook_failures
 WHERE function_name = 'member-gyms-drift' AND resolved_at IS NULL;
```

**Attendu : 1.** Une boîte aux lettres qu'on noie est une boîte qu'on cesse de lire.

Puis réparer et rejouer : **la ligne se referme** (`resolved_at` posé). Sans cela, une divergence corrigée laisserait une alerte éternelle et le cockpit apprendrait à l'ignorer.

### 5. Les deux décomptes de plafond rendent le même chiffre

Mettre un membre dans **deux** salles, salle active = la seconde. Puis comparer :

```sql
-- ANCIEN prédicat (admin-create-member avant ce lot) — salle ACTIVE
SELECT count(*) FROM profiles WHERE gym_id = '<salle 1>' AND role='member' AND deleted_at IS NULL;

-- Prédicat partagé par handle_new_user, booking-guards et désormais admin-create-member
SELECT count(*) FROM member_gyms mg JOIN profiles p ON p.id = mg.member_id
 WHERE mg.gym_id = '<salle 1>' AND p.role='member' AND p.deleted_at IS NULL;
```

**Attendu : le second est plus grand que le premier** (le membre occupe toujours sa place), et les trois gardes rendent désormais ce second chiffre. Avant ce lot, l'inscription et la création par le gérant pouvaient répondre **deux chiffres différents** à « la salle est-elle pleine » — et c'est celui qui **décide d'un refus** qui comptait faux.

## Ce qui a été rapporté sans être codé

**`switch_active_gym` ne peut pas créer la divergence inverse — confirmé.** Il refuse en `PT403 / GYM_NOT_A_MEMBER` toute salle sans adhésion, et l'identité vient de `auth.uid()`, jamais d'un paramètre.

**La suppression laisse la ligne, et c'est cohérent.** C'est un *soft delete* : `deleted_at` + anonymisation, `gym_id` **conservé** (intégrité des stats). Le `ON DELETE CASCADE` de `member_gyms` ne se déclenche donc jamais. La ligne reste alignée sur `profiles.gym_id`, lui aussi conservé, et **tous** les consommateurs joignent `profiles` en filtrant `deleted_at IS NULL` — `booking-guards` avec un `!inner` explicite. Aucune place de plan n'est consommée par un compte supprimé.
⚠️ Le piège à connaître : tout futur décompte sur `member_gyms` **sans** cette jointure sur-compterait.

**Deux décomptes d'affichage restent sur `profiles.gym_id`** → **GYM-339** (`useDashboardStats.ts:94`, `useOnboarding.ts:94`). Hors lot : aucune décision ne s'y adosse. Mais Nico voit un chiffre pendant que le système en applique un autre.
