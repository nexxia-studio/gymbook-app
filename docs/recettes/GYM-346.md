# § 1 — AUDIT : l'achat d'abonnement échoue en staging

## Le verdict, en une ligne

**Mollie a été appelé et a refusé le `POST /v2/payments`.** L'échec n'est pas avant l'appel Mollie, et la raison exacte n'existe nulle part : elle n'est ni journalisée, ni transmise au client.

## Comment on le sait

Le message affiché — « **Paiement impossible. Le paiement a échoué côté prestataire, réessaie.** » — est la concaténation exacte de `payments.error_title` et de `payments.errors.MOLLIE_ERROR` (`locales/fr.json`). Or `MOLLIE_ERROR` n'est renvoyé qu'à **un seul endroit** de `create-subscription` :

```ts
const paymentRes = await fetch('https://api.mollie.com/v2/payments', { … })
if (!paymentRes.ok) {
  const detail = await paymentRes.text()
  return errorResponse(502, `Mollie API a refusé la requête: ${detail}`, 'MOLLIE_ERROR')
}
```

**Journaux `function_edge_logs` (staging, 14/09)** — trois `502` sur `create-subscription` :

| heure (UTC) | |
|---|---|
| 14:14:06 | |
| 14:14:45 | |
| **14:43:22** | 🔴 **après** la reconnexion OAuth de 14:41:38 |

> La troisième tentative est postérieure à la reconnexion réussie : **le jeton n'a jamais été la cause**, et la reconnexion n'a rien changé.

## 🔴 Correction d'une prémisse du cadrage

> « AUCUNE ligne `payments` créée : l'échec est AVANT l'appel Mollie »

**L'inférence ne tient pas.** Dans `create-subscription`, l'`INSERT payments` est la **dernière** étape — après la création du customer Mollie **et** après la création du paiement (c'est le motif de GYM-243 : la ligne a besoin de `mollie_payment_id` et de `checkout_url`, que seule la réponse de Mollie fournit). L'absence de ligne ne prouve donc **rien** sur l'ordre : elle est parfaitement compatible avec un refus de Mollie.

## Les pistes, tranchées

| piste | verdict |
|---|---|
| **a.** paramètre d'exécution anticipée inconnu de la fonction déployée | ❌ **écartée** — source lue sur le déployé (staging, version 39, 10/09 15:38 UTC) : l'import `readEarlyPerformanceConsent` et les deux champs optionnels **y sont**. GYM-336 est bien déployée. Et un champ inconnu ne ferait rien : le body est lu champ par champ. |
| **b.** `resolve_plan_for_payment` ne rend pas le plan | ❌ **écartée** — un plan non résolu rend `PLAN_NOT_FOUND` (« Formule indisponible »), pas ce message. Le plan est bien lu : `Illimité 3 mois`, `recurring_fixed`, 8900 c, EUR, actif. |
| **c.** customer / mandat Mollie | ❌ **écartée** — un échec de création du customer rend `MOLLIE_CUSTOMER_ERROR` (« Échec de la création du mandat »), un autre message. **L'étape customer a donc réussi**, le chemin est bien emprunté. |
| **d.** payload (vat / commission / application fee) | ⚠️ **la seule qui reste** — et les valeurs sont pourtant saines (ci-dessous). |

**Valeurs réelles du payload**, mesurées en SELECT seul :

| champ | valeur |
|---|---|
| `amount` | 89,00 EUR |
| `applicationFee` | **0,89 EUR** (plan `pro`, taux SEPA 1 %, aucun override) |
| `profileId` | présent |
| connexion Mollie | `active` |
| `sequenceType` | `first` · `method: ['directdebit','bancontact','creditcard']` |

Rien n'est numériquement invalide : la commission est très au-dessus du minimum de 0,01 € et très en dessous du montant.

## 🔴 Ce qui oriente vraiment : le même code réussit en production

**Prod** : 13 paiements d'abonnement à l'état `paid`, 8 `member_subscriptions`, le dernier le **10/09** — avec la **même version du code** et le même payload.

Un défaut structurel du payload (`directdebit` en premier paiement, forme de l'`applicationFee`, `sequenceType`) échouerait **aussi en production**. Ce n'est donc pas le code : **c'est le compte Mollie connecté de staging**. Hypothèse la plus probable, à vérifier dans le tableau de bord Mollie du compte de test :

- une **méthode indisponible** sur ce profil — `directdebit` en tête de liste est le premier suspect, le prélèvement SEPA devant être activé explicitement ;
- ou la **capacité à percevoir une `applicationFee`** absente sur une organisation de test non complètement intégrée.

## Le code d'erreur distinct qu'il faudrait rendre

> « Le message *échec côté prestataire* masque la cause — c'est déjà ce qui nous a coûté deux semaines sur GYM-259. »

**Et il y a pire que le message : la cause n'est écrite nulle part.** La branche `MOLLIE_ERROR` **ne journalise pas**. Elle lit `detail` et le place dans un corps HTTP 502 que `mapPaymentError` jette — il ne lit que le `code`. C'est pourquoi les journaux de fonction ne contiennent **aucune** trace des trois échecs.

Proposition, par ordre de valeur :

1. **`console.error` du statut et du corps Mollie** dans cette branche. Une ligne. Sans elle, tout le reste reste invisible. *(C'est ce qui manquait pour clore cet audit en cinq minutes.)*
2. **Distinguer sur le statut HTTP de Mollie** — trois causes que `MOLLIE_ERROR` confond aujourd'hui :

| statut Mollie | code proposé | message | réessayable |
|---|---|---|---|
| **422** (requête refusée : méthode indisponible, fee interdite, montant invalide) | `MOLLIE_PAYLOAD_REFUSED` | « Cette formule ne peut pas être payée en ligne pour l'instant. La salle est prévenue. » | **non** |
| **401 / 403** (jeton, scopes) | `MOLLIE_UNAUTHORIZED` | « Paiement temporairement indisponible. » | non |
| **5xx / réseau** | `MOLLIE_ERROR` (inchangé) | « Le paiement a échoué côté prestataire, réessaie. » | oui |

> 🔴 **« Réessaie » est activement trompeur sur un 422.** Le membre a réessayé « plusieurs fois » — trois tentatives dans les journaux — pour une requête que Mollie refusera identiquement à chaque fois. Le code actuel promet un espoir qui n'existe pas.

3. Remonter `detail` à **Sentry**, jamais au membre.

**Non corrigé dans ce lot**, comme demandé.

# § 2 — L'erreur réseau sur l'acceptation

En mode avion, l'écran affichait **« TypeError: Network request failed »** — un message d'outillage, montré à un membre au moment précis où on lui demande d'accepter un contrat.

**Ce qui change** : la porte ne renvoie plus `rpcErr.message` mais une **clé i18n**, que l'écran traduit — même convention que `mapPaymentError` pour les achats. Deux cas distingués :

| cause | message |
|---|---|
| coupure réseau (aucun `ERRCODE`) | « Impossible d'enregistrer votre acceptation : vérifiez votre connexion et réessayez. » |
| refus serveur (PT401 / PT422 / PT404) | « Impossible d'enregistrer votre acceptation pour le moment. Réessayez dans un instant. » |

**Un `try/catch` a été ajouté autour de la RPC** : `supabase.rpc` rend l'erreur dans `{ error }` la plupart du temps, mais une coupure peut faire **remonter** le `TypeError` de `fetch`. Sans lui, l'exception traversait le hook et laissait le bouton en « chargement » indéfiniment.

⚠️ **La logique de blocage est intacte** : dans les deux cas `status` reste `needed`, l'app ne s'ouvre pas. Le bouton reste actif (`setSubmitting(false)` précède le test), la case reste cochée — on réessaie d'un tap.

**Autres appels réseau non gardés — vérifiés** : `PurchaseConsentSheet` n'en fait **aucun**. `LegalAcceptanceScreen` n'en fait qu'un, `useLegalParams()`, déjà garde-fou par construction (tout échec laisse les valeurs de repli, documenté depuis GYM-197 : « un membre doit TOUJOURS pouvoir lire ses CGU »).

# § 3 — La forme de la case

🔴 **Le texte juridique est identique à l'octet** — vérifié par SHA256 sur `consent_label` en fr et en, et sur les 7 clés du bloc `early_performance`. Seule la mise en forme bouge.

| avant | après |
|---|---|
| formule et prix : une ligne grise centrée sous le titre, **même taille que la clause** | **premier bloc**, nom de la formule en gras/base à l'encre pleine, prix en dessous |
| clause en `leading-relaxed` (~22,75 px) | `leading-6` (24 px) |
| note « Cette demande est enregistrée… » collée à la clause | **séparée par un filet**, `leading-5`, taille et encre discrètes inchangées |
| CTA à `mt-5` | `mt-7` |

> 🔴 **Un piège évité, et c'est le même qu'en GYM-337.** Le bloc prix avait d'abord reçu `tokens.field` comme fond. En single, `field` vaut `#FFFFFF` — soit exactement `surface`, la couleur de la feuille : le bloc aurait été **invisible sur son propre fond chez Dopamine**. La hiérarchie est donc faite par la **typographie seule**, sans aucun fond.

**Parité de jetons, mesurée** : l'ensemble des jetons employés par le fichier est **identique avant et après** — `accentDim`, `actionBg`, `border`, `onAction`, `onBackgroundMuted`, `onSurface`, `onSurfaceSecondary`, `surface`. **Aucune couleur nouvelle n'entre sur cet écran**, donc le garde-fou de contraste n'a rien de neuf à trancher.
