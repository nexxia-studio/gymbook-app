## § 1 — 🔴 Deux assertions RLS qui ne pouvaient pas échouer

### Le défaut

```ts
.update({ name: 'HACKED' }).eq('gym_id', MOVE95_ID)
.select('id', { count: 'exact', head: true })     // ← le 2e argument est IGNORÉ
…
(count ?? 0) === 0                                 // ← donc TOUJOURS vrai
```

Après `.update()` / `.delete()`, on n'est plus sur le `PostgrestQueryBuilder` — dont
`select` accepte `(columns, options)` — mais sur le **`PostgrestTransformBuilder`**, dont
`select` **n'accepte qu'un argument**.

Établi sur le code installé (`@supabase/postgrest-js`, supabase-js 2.105.4) :

| | |
|---|---|
| `PostgrestQueryBuilder.select(columns?, options?)` | `index.d.mts:2890` — 2 arguments |
| `PostgrestTransformBuilder.select(columns?)` | `index.d.mts:1093` — **1 argument** |
| implémentation d'exécution | `index.mjs:556` — `select(columns)`, le 2e argument **n'est jamais lu** |

Aucun en-tête `count` n'est donc posé : `count` vaut `null`, et `(count ?? 0) === 0` est vrai
**quoi qu'il arrive**. Les deux tests concernés —

- `Studio Test CANNOT UPDATE Move95 coaches`
- `Studio Test CANNOT DELETE Move95 activities`

— **passaient au vert avec les RLS grandes ouvertes.** Ce sont exactement les deux
protections en écriture inter-locataires.

### Le correctif

On compte les lignes **renvoyées**. `.select('id')` pose déjà `Prefer: return=representation` :
la liste est vide quand RLS bloque.

```ts
const { data: updRows, error: updErr } = await studio
  .from('coaches').update({ name: 'HACKED' }).eq('gym_id', MOVE95_ID)
  .select('id')
…
!!updErr || (updRows?.length ?? 0) === 0
```

Le `!!updErr` couvre le cas où la politique **lève** au lieu d'affecter 0 ligne. Un UPDATE ou
DELETE bloqué par RLS ne lève pas en général — il affecte 0 ligne — d'où le recours initial
au comptage, et d'où l'erreur.

### Les 11 autres assertions sont saines

Vérifiées une par une : les lectures testent `data.length`, l'INSERT teste `!!insertErr`
(correct — un INSERT bloqué, lui, lève bien).

### ⚠️ Ce que ce lot ne fait PAS

**Le banc n'a pas été exécuté.** Il exige quatre identifiants de staging
(`STAGING_MOVE95_EMAIL`, `STAGING_MOVE95_PASSWORD`, `STAGING_STUDIO_EMAIL`,
`STAGING_STUDIO_PASSWORD`) et `STAGING_ANON_KEY`, dans `apps/dashboard/.env.test` (gitignoré),
absent de ce poste. **Les assertions corrigées sont donc prouvées par le code et par le
contrôle de types, pas par une exécution.**

🔴 **À rejouer sur staging** : `npx tsx src/tests/rls-isolation.test.ts` depuis
`apps/dashboard`. Tant que ce n'est pas fait, **on ignore si les RLS en écriture tiennent
réellement** — les deux tests n'ont jamais rien dit d'autre que « vert ».

## § 2 — `src/tests` n'était contrôlé par rien

`tsconfig.app.json` porte `"exclude": ["src/tests"]`, et aucun autre projet ne les reprenait.
**Deux fichiers hors de tout contrôle** — ceux du § 1.

Le lot ajoute `tsconfig.tests.json`, troisième projet référencé, avec les types **Node**
(le banc tourne sous `tsx`, pas dans le navigateur). L'`exclude` de `tsconfig.app.json`
**reste** : les fichiers appartiennent désormais au troisième projet, l'exclusion évite la
double inclusion.

### Le piège est refermé — prouvé

Bug d'origine réintroduit délibérément, puis `npx tsc --build` :

```
src/tests/rls-isolation.test.ts(206,19): error TS2554: Expected 0-1 arguments, but got 2.
exit=2
```

**C'est exactement l'erreur qui aurait arrêté le § 1**, des semaines plus tôt.

### Cinq alias resserrés, sans changement de comportement

Les gardes `if (!X) throw` existaient déjà et suffisent à l'exécution, mais ne resserrent pas
le type : `signIn` et `main` sont des **déclarations** de fonction, donc hoistées, et le
resserrement obtenu au niveau du module ne les traverse pas. Cinq `const` figent les valeurs
après les gardes. **Messages d'erreur et comportement rigoureusement identiques.**

## § 3 — `get-progression` ne compilait pas

2 × `TS2352` (lignes 171 et 191), issues de **GYM-57** — pas des lots de la semaine. La
fonction est **en production**, consommée par l'onglet studio (`apps/mobile/hooks/useProgression.ts`).

Jamais vue parce que `deno check` n'a toujours été lancé que sur les fonctions touchées par
chaque lot.

**Diagnostic : bruit de typage, sans impact d'exécution.** `bookings → time_slots` est une
relation vers-un : PostgREST rend un objet ; ce sont les types générés qui l'annoncent en
tableau. Le code se protège déjà (`Array.isArray(ts) ? ts : [ts]`).

**Correctif : `as unknown as`** — le remède que TypeScript indique lui-même dans le message
TS2352. Un cast est **entièrement effacé à la compilation**. Diff hors commentaires, les deux
seuls changements :

```diff
-        const ts = (row as { time_slots: … }).time_slots
+        const ts = (row as unknown as { time_slots: … }).time_slots
```

⚠️ **La lecture défensive est laissée telle quelle.** `arr[0]?.activities?.name` rendrait
`undefined` si `activities` était un tableau. Traiter ce cas serait un **changement de
comportement** sur une fonction en production — hors cadrage de ce lot. Si `cours_favori` ou
`coach_favori` remontent vides en production, c'est la première piste.
