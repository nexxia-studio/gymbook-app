## § 1 — `openCheckout` dit enfin ce qui s'est passé

### Avant

```ts
export async function openCheckout(url: string): Promise<void> {
  await WebBrowser.openBrowserAsync(url)   // ← le résultat est JETÉ
}
```

### Après

```ts
export interface CheckoutOpenOutcome {
  presented: boolean   // INFÉRÉ — voir le seuil ci-dessous
  type: string         // BRUT : 'opened' | 'cancel' | 'dismiss' | 'locked' | 'threw'
  elapsedMs: number    // BRUT — le signal discriminant sur iOS
  detail?: string
}
```

```
[openCheckout] platform=ios type=locked elapsedMs=3 presented=false
```

### 🔴 Pourquoi le DÉLAI, et pas seulement le type

Les deux plateformes ne résolvent pas au même moment :

| | quand la promesse résout | type rendu |
|---|---|---|
| Android | **aussitôt** | `opened` |
| iOS | à la **FERMETURE** du navigateur | `cancel` (le membre) / `dismiss` (programmatique) |

Sur iOS, un `cancel` est donc **normal** après un vrai affichage. Ce qui ne l'est pas, c'est
un `cancel` rendu instantanément : l'animation de présentation dure à elle seule ~300 ms.

`PRESENTATION_FLOOR_MS = 400`. ⚠️ **Seuil heuristique, assumé comme tel** — c'est pourquoi
`type` et `elapsedMs` sont journalisés **bruts** et rendus à l'appelant. Si le seuil est mal
placé, la mesure reste lisible et le diagnostic n'en dépend pas.

### Un échec d'ouverture alerte désormais Sentry

Ce n'est pas un refus métier — le membre n'a rien refusé, il n'a rien pu voir. Même doctrine
que GYM-270 pour les échecs d'infrastructure.

## § 3 — La cause probable, trouvée dans le code natif — NON corrigée

### ⚠️ D'abord, une rectification : la piste « transition de navigation » ne tient pas

Le cadrage dit « Les deux chemins partagent ce motif ». **Mesuré dans le code : non.**
`PaymentRequiredSheet.runDropIn` **ne navigue pas** — son seul `router.push` appartient à un
autre CTA (`goToSubscription`). Une transition de navigation ne peut donc pas expliquer
l'échec de 16h03.

### Ce que les deux chemins partagent réellement

`expo-web-browser/ios/WebBrowserModule.swift` :

```swift
if vcDidPresent { currentWebBrowserSession = nil; vcDidPresent = false }
guard currentWebBrowserSession == nil else {
  promise.resolve(["type": "locked"])   // ← résout AUSSITÔT, sans rien présenter
  return
}
```

et `WebBrowserSession.open()` :

```swift
var currentViewController = UIApplication.shared.keyWindow?.rootViewController
while currentViewController?.presentedViewController != nil { … }
currentViewController?.present(viewController, animated: true) { self.didPresent() }
//                   ↑ ce `?` avale silencieusement le cas keyWindow == nil
```

**L'enchaînement :** si une présentation n'aboutit jamais, `didPresent` ne part pas →
`vcDidPresent` reste `false` → `currentWebBrowserSession` reste non nul → **tous les appels
suivants rendent `locked`, instantanément, jusqu'au redémarrage de l'app.**

C'est la seule hypothèse qui explique que **deux chemins différents, à 29 minutes
d'intervalle, échouent à l'identique** sans rien lever.

⚠️ `'locked'` **n'est pas dans les types publics** d'expo-web-browser. Il est dans le code
natif. Une app qui lit `result.type` avec les types fournis ne peut pas le voir venir.

### Ce que ce lot fait, et ne fait pas

- **Fait** : reconnaît `locked` explicitement, le journalise, le court-circuite de
  l'heuristique de délai (c'est un échec **certain**, pas inféré), et envoie à Sentry un
  message distinct disant que **tous** les achats échoueront jusqu'au redémarrage.
- **Ne fait pas** : la correction. `WebBrowser.dismissBrowser()` déverrouillerait la session
  fantôme — `dismiss` sur un contrôleur non présenté appelle quand même son complétion, donc
  `finish` et la remise à nil. **Mais c'est fondé sur une lecture de code, pas sur une
  mesure.** Le journal dira `locked` ou autre chose au prochain essai, et c'est cette mesure
  qui doit décider.

### Ce que le prochain essai tranchera, en une ligne

| ce que dira le journal | conclusion |
|---|---|
| `type=locked elapsedMs<10` | session fantôme confirmée → appliquer `dismissBrowser()` + retenter |
| `type=cancel elapsedMs<400` | la présentation elle-même échoue → chercher côté `keyWindow` |
| `type=threw` | le module lève → le message dira quoi |
| `type=cancel elapsedMs>400` | le navigateur S'EST ouvert → le défaut est ailleurs |

## § 4 — L'écran cesse de mentir

Au bout de 5 minutes, l'écran affichait **toujours** « Ton paiement est bien enregistré… tes
séances seront créditées automatiquement, tu n'as rien à faire. » Le 17/09 c'était **faux** :
aucun paiement n'avait eu lieu.

Trois situations, trois phrases :

| cas | quand | ce qu'on dit |
|---|---|---|
| `not_opened` | `checkout_opened=0` — l'app sait que le navigateur ne s'est pas ouvert | la page ne s'est pas ouverte, rien n'a été débité |
| `not_finalized` | la ligne n'a jamais quitté `pending`/`open` | le paiement n'a pas été terminé, rien n'a été débité |
| `awaiting` | tout le reste | message d'origine — **c'est le seul cas où il est vrai** |

⚠️ **DEUX SIGNAUX INDÉPENDANTS, ET C'EST VOULU.** `checkout_opened` repose sur l'heuristique
de délai du § 1 ; le statut de la ligne est un **fait serveur**. Si l'heuristique se trompe,
`not_finalized` rattrape le cas — le membre n'est jamais renvoyé au « tu n'as rien à faire »
alors qu'il lui reste tout à faire. Dans l'incident du 17/09, le statut était `pending` :
le second signal seul aurait suffi.

`awaiting` conserve le plafond de 5 min et sa raison (GYM-207 : crédit reçu en 2 min 33 s le
04/08, au-delà de l'ancien plafond de 2 min).

⚠️ **FORMULATION À VALIDER** — « propose, je valide ». Les six libellés sont dans
`apps/mobile/locales/{fr,en}.json`, clés `payment.not_opened_*`, `payment.not_finalized_*`,
`payment.awaiting_*`.

⚠️ **NON TRAITÉ, À TRANCHER** : au retour dans l'app, `AppState` relance un poll de 5 min
quand le statut est `timeout`. Légitime pour `not_finalized` (le membre a pu payer entre
temps), inutile pour `not_opened`. Les boutons n'ont pas été touchés non plus — tu as
prescrit le message, pas les actions.

## § 5 — Ce qui n'a PAS été touché

**L'ordre `router.push` → `openCheckout` est intact.** L'écran de vérification reste monté
avant le navigateur : c'est l'intention de GYM-96, pour que le poll et le filet `AppState`
soient armés quel que soit le mode de retour. La consigne était de mesurer avant de
réordonner — et le § 3 montre que réordonner n'aurait probablement rien réglé.

**`await` non ajouté dans `PaymentRequiredSheet`**, volontairement : sur iOS la promesse ne
résout qu'à la fermeture du navigateur ; attendre y suspendrait la fonction pendant tout le
paiement, alors que le poll des crédits doit tourner **pendant**. Le verdict est lu à part,
quand il arrive.

**Piste 3 écartée** : `expo-web-browser` est en `~15.0.11`, installé, présent depuis le
bootstrap (`ce17635`) — aucun changement de version. Un module non lié lèverait
`Cannot find native module`, ce qui aurait atteint Sentry ; aucun événement n'y figure.
